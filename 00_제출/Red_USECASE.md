# Red 유스케이스 다이어그램

[프로젝트 기준 문서](Red_PROJECT.md) v1.1과 제공된 유스케이스 강의자료 21장을 바탕으로 작성한 설계 초안임 한 화면 구성을 유지하면서 기존 10개 기능 범주를 32개 세부 행동으로 분리함 기존 ‘사용자’·‘사업체 운영자’·‘서비스 운영자’의 역할과 이용 범위는 유지하며 구현 완료를 뜻하지 않음

## StarUML 원본과 미리보기

[StarUML 편집 원본 열기·다운로드](Red_USECASE.mdj) · [SVG 미리보기](assets/Red_USECASE.svg) · [PNG 미리보기](assets/Red_USECASE.png)



수정 기준은 `Red_USECASE.mdj`임 StarUML의 액터·유스케이스·시스템 경계·연관·include 모델과 배치 정보를 담은 편집 원본임 **File → Open**으로 연 뒤 모델 탐색기의 **유스케이스 모델 → 전체 유스케이스**를 선택함

| 도면 | 표시하는 기능 | 이용 액터 |
| --- | --- | --- |
| 전체 유스케이스 | 기존 UC01부터 UC10까지를 세분화한 32개 행동과 관계 | 사용자·사업체 운영자·서비스 운영자 |

가로 3200 × 세로 1800의 16:9 한 화면에 시스템 경계 하나, 액터 3개, 세부 유스케이스 32개를 표시함 화면 안의 네 묶음은 배치를 위한 구분이며 각각 별도 시스템을 뜻하지 않음 각 액터는 한 번만 표시하며 실선 연관 58개와 필수 포함 관계 16개를 연결함

색상은 실선이 어느 액터와 연결되는지를 구분함 같은 액터 또는 같은 포함 대상을 잇는 선은 일부 구간을 겹쳐 그렸으며, 원본에는 각 관계를 별도 모델로 보존함 선의 분기는 처리 순서나 조건 분기를 뜻하지 않음 점선 화살표는 필수 포함, 노란 타원 두 개는 선택·검토 중인 F04 기능을 뜻함

StarUML 7.1.1에서 전체 도면 하나의 로드·SVG 내보내기를 검증함 앱의 미등록 내보내기에는 워터마크가 표시되므로 미리보기는 원본 모델·좌표에서 별도로 생성함 앱 내보내기 이미지를 수정한 결과가 아님 PNG의 실제 표시와 모델·미리보기의 연결 관계, 문서의 표·링크 구조를 대조함 앱 화면에서 수동 편집 후 저장하는 동작과 Obsidian 읽기 화면은 직접 확인하지 못함

## 사용자와 범위

| 액터 | 역할 | 이용 범위 |
| --- | --- | --- |
| 사용자 | 일반 조회 역할이며 세부 범위는 설계 가정 | UC01의 두 조회·비교와 UC02의 일곱 분석·제안 조회를 직접 이용함 모두 UC10을 포함함 비공개 일정표·기록과 운영 관리에는 연결하지 않음 |
| 사업체 운영자 | 카페 또는 체험 활동 업체 운영자·홍보 담당자 | 기존 UC01부터 UC06까지에서 분리한 23개 행동을 직접 이용함 F04 두 행동은 도입할 경우에만 제공함 본인 사업체의 계획·기록을 이용함 |
| 서비스 운영자 | 프로젝트 팀의 개발·자료 분석·검증 담당자 | 사업체 운영자와 공통인 23개 행동에 CSV 등록과 추천 기준 설정·근거 기록을 더한 26개 행동을 직접 이용함 비공개 사업체 계획·기록은 권한 또는 동의가 있는 범위로 제한함 |

‘사용자’는 기존 두 운영자와 별도로 둔 일반 조회 역할이라는 설계 가정을 유지함 관광객 대상 상품·예약 기능이나 일반 공개 서비스 도입을 확정한 뜻은 아니며 실제 제공 대상과 접근 정책은 별도로 정함

사업체 운영자는 실제 홍보 활동을 수행하고 시스템에는 그 기록을 입력함 클릭·예약·쿠폰 관련 타원은 확보한 결과를 기록하는 행동이며 광고 게시·예약 대행·쿠폰 발행 기능이 아님

## include 관계

| 기본 행동 | 반드시 포함하는 행동 | 관계 수 |
| --- | --- | --- |
| UC01-1·UC01-2와 UC02-1부터 UC02-7까지 | UC10 자료 출처·기준 표시 | 9개 |
| UC03-1 일정표 작성·UC03-2 일정표 수정 | UC03-3 일정표 저장 | 2개 |
| UC07 CSV 자료 등록 | UC08-1부터 UC08-5까지의 기간·집계·지역 코드·누락값·제공 기준 검증 | 5개 |

화살표는 포함되는 행동을 향함 출처 표시에서 필수인 것은 시스템의 표시 동작이며, 사용자가 별도 확인 버튼이나 별도 화면을 열어야 한다는 뜻이 아님

이번 상세 설계에서는 일정표 작성·수정의 성공 완료를 저장 성공으로 정의하여 저장을 필수 포함 처리로 둠 저장이 실패하면 해당 작성·수정은 성공 완료가 아님 사용자는 명시적으로 저장 기능도 이용할 수 있음 저장한 일정표의 조회에는 작성·수정·저장을 포함시키지 않음

등록 자료는 다섯 검증을 모두 거치며 비교할 수 없거나 검증에 실패한 자료를 정상 비교 자료로 취급하지 않음 입력 여섯 행동을 서로 include로 연결하지 않으며, 미확보 결과가 있을 수 있다는 조건을 유지함

분리된 기능을 모두 필수 순서로 연결하지 않음 F01·F02·F03 사이의 선후 흐름이나 ‘작성 → 수정 → 저장 → 조회’ 순서를 include로 표현하지 않음 저장한 계획을 볼 때 분석을 매번 다시 실행해야 한다는 요구사항도 추가하지 않음

## 선택 기능과 AI 에이전트

F04는 ‘추천 이유 설명 초안 작성’과 ‘보고서 초안 작성’ 두 선택 기능으로 분리함 선택 구현이라는 이유만으로 `<<extend>>` 관계를 추가하지 않음 실행 중 어떤 조건에서 기존 기능을 확장하는지가 정해져야 해당 관계를 사용할 수 있음

강의자료의 단골 고객 할인은 멤버십 가입 조건과 주문할 책 입력 완료라는 확장 시점이 있고, 신용카드 지불은 신용카드를 선택한 경우라는 조건이 있음 현재 F04에는 어느 기본 유스케이스의 어느 시점에서 확장할지가 정해져 있지 않아 독립된 선택 유스케이스로 표시함 이후 확장 관계를 정의할 경우 화살표는 추가 기능에서 기본 유스케이스를 향하도록 작성함

대화에서 제안한 AI 에이전트의 가게 조건 질문·계획 초안 작성·수정은 아직 도입이 확정되지 않아 이번 기준 다이어그램에는 넣지 않음 F04를 AI 에이전트 기반 기능으로 확대하기로 결정하면 프로젝트 문서와 유스케이스 범위를 함께 갱신함

## 이번 그림에 추가하지 않은 내용

- 로그인·회원가입: 접근 권한 보호는 필요하지만 구체적인 인증 방식과 화면은 아직 정하지 않아 별도 기능으로 추가하지 않음
- 외부 데이터 플랫폼 액터: 현재 계획은 운영자가 CSV를 확보해 등록하는 방식이며, 외부 플랫폼과 자동으로 통신하는 구조는 확정되지 않음
- 외부 AI 서비스 액터: AI 사용 여부와 제공 업체·연결 방식이 정해지지 않아 추가하지 않음 시스템 내부 기능을 별도 사용자로 표시하지 않음
- 자동 광고 실행·결제·예약 대행, 실시간 혼잡도, 개인별 이동·결제 추적, 매출 증가 보장: 기존 프로젝트의 제외 범위를 유지함

## 검토 기준

- 기존 액터 두 역할과 F01부터 F04까지는 프로젝트 기준 문서와 맞추고, 추가한 ‘사용자’의 일반 조회 범위는 설계 가정으로 구분함
- 일정표의 작성·수정·저장·다시 보기와 실행 기록·결과 비교가 빠지지 않았는지 확인함
- 필수 기능, 선택 기능, 운영 지원과 제외 범위를 구분함
- 실선 관계와 include 화살표의 방향, 한글 표시와 그림 잘림을 확인함

| 항목 | 반영 내용과 검증 기준 |

| 유스케이스 이름 | ‘조회’·‘관리’·‘입력’·‘작성’·‘등록’·‘검증’·‘표시’처럼 행위를 뜻하는 명사를 사용함 입력·검증은 요청에 따라 보조 행동까지 세분화하고 구현 기술은 별도로 설명함 |

| 포함 관계 | 분석·제안 조회 9개 → 출처 표시, 일정표 작성·수정 → 저장, CSV 등록 → 다섯 검증의 방향과 필수 조건을 확인함 |

| 명세 조건 | 출처·기간·집계 기준 표시, 자료 부족·기준 불일치 안내, 미확보 기록과 0건의 구분, 비공개 기록의 권한·동의 조건을 유지함 |
