## 2. ERwin에서 직접 해야 하는 작업

### 2.2 물리 화면에 자료형 표시

**확인 완료** Red_ERD.erwin의 물리 화면은 PDF 51쪽, 52쪽, 54쪽 예시처럼 컬럼 이름 옆에 자료형과 NULL 여부가 보이게 저장되어 있음 (2.1의 물리 화면 그림) 표시가 사라졌을 때만 아래 순서로 다시 켬

1. 도구 모음의 Logical/Physical 선택 상자에서 **Physical**을 고름 (PDF 44쪽의 Physical Model 전환과 같은 동작)
2. **Format → Display Level → Column**을 고름
3. **Format → Table Display → Column Datatype**에 체크함 PDF 54쪽처럼 NULL 여부까지 보이려면 **Null Option**도 체크함
4. 다시 **Logical**로 바꾸고 **Format → Display Level → Attribute**인지 확인함
5. 저장함

메뉴가 보이지 않으면 다이어그램의 빈 곳을 오른쪽 클릭해 같은 이름의 메뉴를 찾음

### 2.3 SQL 스키마와 테이블 명세서

PDF 47쪽, 53쪽, 55쪽의 순서를 따름

**SQL은 3차 수정에서 만들었음** → [Red_ERD_Oracle.sql](Red_ERD_Oracle.sql) 물리 화면에서 Tools → Forward Engineer → Schema Generation을 기본 옵션으로 실행하고 Report로 저장한 것임 테이블 13개, PK 13개, AK 4개, FK 17개이고, ERwin 기본 옵션이라 관계 규칙을 확인하는 트리거 30개도 들어 있음 ([수정 내역 0.5](ERD_수정_내역.md#05-sql-스키마-생성-결과))

1. ERD를 고친 뒤에는 같은 메뉴로 SQL을 다시 만들어 이 파일을 바꿈 Preview로 CREATE TABLE 문장을 먼저 확인함
2. Oracle은 VARCHAR 길이를 기본적으로 바이트로 세서 한글이 적게 들어감 ERD의 길이는 화면과 같은 글자 수 기준이므로, SQL을 실행하기 전에 `ALTER SESSION SET NLS_LENGTH_SEMANTICS = CHAR;`를 먼저 실행해 글자 수로 세게 함 (프로토타입 대조 가이드 P8)
3. 이 SQL은 아직 Oracle DB에서 실행해 보지 않았음 처음 실행할 때 오류가 없는지 확인함
4. 수업에서 제공한 테이블 명세서 서식으로 작성함 ERD의 물리 이름을 '컬럼명', 논리 이름을 '설명'에 쓰고 KEY 구분, Null, Unique, DataType, 길이는 Red_ERD.erwin의 설정과 같게 씀 [수정 내역 3장](ERD_수정_내역.md#3-현재-테이블과-컬럼-3차-수정-후)의 표를 옮겨 쓰면 됨
5. FK 목록에는 관계 이름(BusinessUser 등), 관련 테이블, 컬럼명을 씀 ([수정 내역 4장](ERD_수정_내역.md#4-현재-관계-3차-수정-후))
6. 월 값 컬럼(TARGET_MONTH, START_MONTH, END_MONTH, STAT_MONTH)의 비고에 '매월 1일로 저장'을 적음 (검토 보고서 ③)
7. 홍보 계획의 참고사항에 '같은 사업체에 같은 홍보 제안을 두 번 담지 못하게 하는 확인은 프로그램에서 함'을 적음 (프로토타입 대조 가이드 P17)
8. 코드값 컬럼의 참고사항에는 PDF 55쪽 예시처럼 '코드 설계서 참조'를 적음 → [ERD 코드 설계서](ERD_코드_설계서.md) 같은 문구가 ERwin 각 컬럼의 Definition에도 있음
9. REGION_CONSUMPTION_STAT.SHARE_RATE의 비고에 '비율에 소수가 있어 교안의 숫자형 INTEGER 규칙의 예외로 NUMBER(5,2)를 씀'을 적음
10. PROMO_PLAN의 참고사항에 '계획의 지역은 사업체 지역을 따름 제안에서 담을 때는 그 사업체 지역의 제안만 담을 수 있게 프로그램에서 확인함'을 적음 (수정 내역 0.8)

## 3. 팀이 정해야 하는 부분

### 3.1 Q1부터 Q7까지의 결정 결과

PDF 13쪽의 논리적 모델링 과정(상세 속성 추출 → 정규화 → 데이터 표준화)과 정규화 기준(PDF 29쪽부터 34쪽까지)으로 남겼던 질문임 팀 수정본의 선택과 화면 시안의 동작을 바탕으로 2차 수정에서 정했고, Q4와 Q6은 3차 수정에서 검토 보고서에 따라 바꿈

| 번호 | 질문 | 결정 | 근거 | 남은 일 |
| --- | --- | --- | --- | --- |
| Q1 | 출처 및 기준 기간을 나눌까 | 출처 SOURCE_INFO, 기준 기간 BASE_PERIOD로 나눔 (팀 결정) | 1정규형 원자값 (32쪽) | 화면 시안의 '분석 결과·출처·기준기간·단위' 입력 칸 하나를 나눠야 함 |
| Q2 | 결과 및 수집 방법을 나눌까 | 결과 내용 RESULT_MEMO, 수집 방법 COLLECTION_METHOD로 나눔 (팀 결정) | 1정규형 원자값 (32쪽) | 화면 시안의 '결과와 수집 방법' 입력 칸을 나눠야 함 |
| Q3 | 관광지·상품 후보를 따로 둘까 | '제안 항목' 엔터티로 옮기고 항목마다 내용과 이유를 저장함 | 화면이 항목마다 이유를 보여줌, 1차 정규화 (31쪽) | 없음 |
| Q4 | 소요 시간은 어디에 둘까 | **3차 수정에서 바꿈** 실행 결과 기록의 '계획 소요 시간' SPENT_TIME_MIN | 기록 입력 팝업(SCR-B-002-P01)에서 입력함 (검토 보고서 ⑧) | 없음 |
| Q5 | 추천 채택 여부를 지울까 | 지우지 않고 ADOPTION_STATUS로 둠 | 화면이 직접 고르는 값이라 홍보 계획의 홍보 제안 ID와 뜻이 다름 | 없음 |

| Q7 | 테이블 이름에 TBL_을 붙일까 | 붙이지 않고 그대로 둠 | 51쪽, 52쪽, 53쪽, 55쪽 예시는 TBL_을 쓰지만 54쪽 예시와 규칙 문장에는 없음 | 수업에서 요구하면 Table Properties에서 이름을 바꾸고 테이블 명세서도 같이 고침 |

### 3.2 검토 보고서에서 팀 결정으로 남긴 항목

검토 보고서가 '팀 결정'으로 남긴 네 항목은 화면설계서와 화면 시안을 근거로 아래처럼 정해 반영함 팀이 다르게 정하면 '다르게 정하면' 칸대로 고침

| 번호 | 결정 | 근거 | 다르게 정하면 |
| --- | --- | --- | --- |
| ③ 월 값 자료형 | DATE (매월 1일) | PDF 51쪽 날짜형 DATE | 'YYYY-MM' 문자로 하려면 지역 소비 통계의 기준 월까지 다섯 컬럼을 같은 VARCHAR 길이로 함께 바꾸고 명세서 비고에 형식을 적음 |
| ⑤ 활용 사례 | 엔터티를 만들지 않음 (정적 콘텐츠, DB 미저장) 화면설계서 SCR-C-002와 ERwin 모델 설명에 적음 | 화면설계서 SCR-C-002에 사례는 검증 전 예시이고 별도 사례 상세 화면이 없다고 적혀 있음 | 사례를 DB에서 조회하려면 '활용 사례' 엔터티(지역·업종·가게·활동·성과·기준)를 만들고 지역, 사업체와 관계를 연결함 |
| ⑧ 소요 시간 위치 | 실행 결과 기록 | 기록 입력 팝업에서 입력하고 빈칸은 미측정으로 둠 | 홍보 계획으로 되돌리면 실행 결과 기록의 SPENT_TIME_MIN을 지우고 홍보 계획에 같은 이름으로 다시 만듦 |
| ⑩ 홍보 계획의 지역 코드 | **지움** (팀 결정, 2026-10-11) 계획의 지역은 사업체 지역을 따름 | 화면 시안도 계획 지역과 가게 지역을 같은 값으로 쓰고, 다른 지역을 대상으로 한 계획은 범위 밖임 3정규형 (34쪽) | 다른 지역을 대상으로 한 계획(팝업, 행사 등)이 필요해지면 지역과 홍보 계획 사이에 비식별 관계를 다시 만들고, 화면설계서에 그 업무 규칙을 적음 |

### 3.3 팀이 확인할 값

화면 시안에 제한이 없어 임시로 정한 값임 실제 자료를 보고 바꾸면 Column Properties에서 Physical Data Type을 고침 (46쪽)

| 컬럼 | 임시 값 | 확인할 내용 |
| --- | --- | --- |
| RECOMMENDATION_CRITERIA.BASE_PERIOD | VARCHAR(50) | 기준 기간을 어떤 글자로 적는지 |
| EXECUTION_RECORD.COLLECTION_METHOD | VARCHAR(200) | 수집 방법 입력 칸의 최대 길이 |
| PROMO_SUGGESTION의 DESCRIPTION, REASON, TITLE | VARCHAR(200), VARCHAR(200), VARCHAR(100) | 제안 문장의 최대 길이 |
| PROMO_SUGGESTION_ITEM의 ITEM_CONTENT, ITEM_REASON, CHECK_NOTE | 모두 VARCHAR(200) | 항목 문장의 최대 길이 |
| REGION_CONSUMPTION_STAT.SHARE_RATE | NUMBER(5,2) | 비중을 소수 둘째 자리까지 저장하는지 (100.00까지 들어감) |
| 코드값 이름 | [ERD 코드 설계서](ERD_코드_설계서.md) | 코드 이름을 바꾸면 VARCHAR 길이도 함께 확인 |

ERwin에서 고치는 방법

- 속성 추가·삭제·이동: 논리 화면에서 엔터티 상자 안의 속성을 고침 (39쪽)
- 엔터티 추가와 관계 연결: 도구 모음의 엔터티 도구와 1:N 식별·비식별 관계 도구를 사용함 (37쪽, 40쪽) 관계 이름과 Null Option은 관계선 오른쪽 클릭 → Properties에서 [수정 내역 4장](ERD_수정_내역.md#4-현재-관계-3차-수정-후)과 같은 방식으로 정함 (42쪽)
- 자료형: 물리 화면에서 테이블 오른쪽 클릭 → Column Properties (46쪽)
- 속성을 지우고 다시 만들면 물리 이름이 한글, 자료형이 CHAR(18)로 돌아가므로 Column Properties에서 다시 정함 (2차 수정의 E2 오류가 이렇게 생겼음)
- 속성의 **Logical Only**, 컬럼의 **Physical Only**는 체크하지 않음 체크하면 한 화면에만 보여 논리 모델과 물리 모델이 서로 달라짐 (검토 보고서 ①)
- 바꾼 내용은 [ERD 수정 내역](ERD_수정_내역.md)에 날짜와 함께 적음
