# ERD 프로토타입 대조 가이드

- 작성일: 2026-10-10
- 프로젝트: 제주 비수기 상권 마케팅 캘린더
- 비교한 것: [Red_ERD.erwin](Red_ERD.erwin) (수정본)과 화면 시안 프로토타입 [app.js](../../02_제품/화면시안/app.js)
- 함께 볼 문서: [ERD 수정 가이드](ERD_수정_가이드.md)의 Q1부터 Q7까지는 강의자료 기준 질문이고, 이 문서의 P1부터 P27까지는 프로토타입 기준 항목임

수정본 ERD는 강의 형식(IE 표기, 관계 이름, NULL 옵션, 대문자 이름, 자료형)을 맞췄지만, 엔터티와 속성 내용은 원본 그대로이고 글자 수는 임시값임 그래서 프로토타입 화면에서 입력하거나 보여주는 값과 맞지 않는 곳이 있음 이 문서는 그 차이를 항목마다 정리하고, 바꾸기로 하면 ERwin에서 무엇을 하면 되는지 적음

> **반영 상태 (2026-10-11)** P1부터 P27까지 모두 [Red_ERD.erwin](Red_ERD.erwin)에 반영함 팀 결정 항목(P2, P8, P15, P17, P22, E)을 어떻게 정했는지는 [ERD 수정 내역 1.3](ERD_수정_내역.md#13-프로토타입-대조-가이드-반영)에 적음 아래 표의 '지금 상태'는 이 문서를 쓴 2026-10-10의 상태임

## 0. 이 문서 읽는 법

- 표 한 줄이 고칠 곳 하나임
- **지금 상태**는 Red_ERD.erwin에 저장된 값, **프로토타입 기준**은 화면 시안 코드에서 확인한 값, **쉽게 말하면**은 왜 문제인지, **바꾸기로 하면**은 ERwin에서 할 일임
- 근거 링크의 숫자는 app.js의 줄 번호임 GitHub에서 누르면 그 줄로 이동함
- A부터 D까지는 컬럼 값만 고치거나 컬럼을 더하면 되는 일이고, E는 엔터티를 새로 만들지 팀이 정해야 하는 일임
- 'PDF'는 「[8주차] 정보시스템 프로젝트 설계 Data Modeling」 강의자료를 뜻함

### 용어 풀이

| 용어 | 뜻 |
| --- | --- |
| NULL / NOT NULL | 값을 비워 둘 수 있으면 NULL, 반드시 있어야 하면 NOT NULL |
| VARCHAR(n) | 글자를 최대 n만큼 저장하는 칸 |
| 코드값 | 정해진 몇 가지 값 중 하나만 저장하는 방식 (예: 실행함, 미실행, 확인 중) 각 값의 뜻은 코드 설계서에 적음 |
| UNIQUE | 같은 값이 두 번 들어가지 못하게 막는 규칙 |
| Cardinality | 부모 하나에 자식이 몇 개 붙을 수 있는지 (0개 이상, 0개 또는 1개 등) |
| CASCADE | 부모를 지우면 연결된 자식도 함께 지우는 규칙 |

## 2. A. 글자 수가 프로토타입보다 짧은 컬럼

화면에서는 254자까지 입력할 수 있는데 DB 칸이 100자면, 긴 값을 저장할 때 오류가 남 DB 칸은 화면 제한과 같거나 커야 함

| 번호 | 대상 | 지금 상태 | 프로토타입 기준 | 쉽게 말하면 | 바꾸기로 하면 |
| --- | --- | --- | --- | --- | --- |
| P1 | USERS.EMAIL | VARCHAR(100) | 로그인(SCR-C-001) 이메일 최대 254자 ([291줄](../../02_제품/화면시안/app.js#L291)) | 101자가 넘는 이메일은 저장되지 않음 | VARCHAR(254) |
| P2 | USERS.PASSWORD | VARCHAR(50) | 비밀번호 최대 128자 입력 ([292줄](../../02_제품/화면시안/app.js#L292)) | 비밀번호는 입력한 그대로 저장하지 않고, 되돌릴 수 없게 바꾼 값(해시)을 저장함 해시 방식에 따라 필요한 길이가 다름 | 이름을 PASSWORD_HASH로 바꾸고 VARCHAR(255) 팀 결정: 해시 저장 방식 |
| P3 | DATA_SOURCE.SOURCE_VERSION | VARCHAR(50) | 자료·기준 관리(SCR-A-001) 자료 출처·버전 최대 120자 ([238줄](../../02_제품/화면시안/app.js#L238)) | 긴 출처 이름이 잘림 | VARCHAR(120) |
| P4 | RECOMMENDATION_CRITERIA.SOURCE_PERIOD_INFO | VARCHAR(200) | 추천 기준 편집(SCR-A-001-P02) '분석 결과·출처·기준기간·단위' 최대 250자 ([276줄](../../02_제품/화면시안/app.js#L276)) | 201자부터 250자까지의 입력은 저장되지 않음 | VARCHAR(250) |
| P5 | RECOMMENDATION_CRITERIA.REASON_TEMPLATE, REQUIRED_CONDITION | 둘 다 VARCHAR(200) | 추천 판단 이유, 적용 조건 각각 최대 500자 ([276줄](../../02_제품/화면시안/app.js#L276)) | 화면에서 허용한 길이의 절반도 안 됨 | 두 컬럼 모두 VARCHAR(500) |
| P6 | PROMO_PLAN.PREPARATION_NOTE | VARCHAR(200) | 계획 작성·수정(SCR-B-001-P01) 준비할 내용 최대 500자 ([355줄](../../02_제품/화면시안/app.js#L355)) | 위와 같음 | VARCHAR(500) |
| P7 | EXECUTION_RECORD.RESULT_MEMO | VARCHAR(200) | 기록 입력·수정(SCR-B-002-P01) 결과와 수집 방법 최대 500자 ([361줄](../../02_제품/화면시안/app.js#L361)) | 위와 같음 | VARCHAR(500) |
| P8 | 한글을 저장하는 모든 VARCHAR 컬럼 | 길이를 세는 단위가 정해지지 않음 | 화면 제한은 모두 글자 수 기준 | Oracle은 기본적으로 바이트 수로 세고, UTF-8 문자 집합에서는 한글 1자가 3바이트를 차지함 그래서 VARCHAR(100)에 한글은 약 33자만 들어감 예를 들어 PROMO_PLAN.TITLE은 70자 제한이라 MySQL이면 VARCHAR(100)으로 충분하지만 Oracle이면 부족함 | Oracle로 정하면 VARCHAR2(70 CHAR)처럼 글자 단위로 적거나 길이를 3배로 잡음 MySQL로 정하면 숫자를 그대로 둠 팀 결정: 최종 DBMS |

## 3. B. 화면에서는 꼭 입력하는데 ERD에서는 비워 둘 수 있는 컬럼

프로토타입은 아래 값이 없으면 저장되지 않음 DB도 같은 규칙을 가져야 나중에 만드는 서버나 관리 도구에서 빈 값이 들어가는 것을 막을 수 있음 선택 상자는 항상 값 하나가 골라져 있으므로 필수로 봄

| 번호 | 대상 | 지금 상태 | 프로토타입 기준 | 쉽게 말하면 | 바꾸기로 하면 |
| --- | --- | --- | --- | --- | --- |
| P9 | PROMO_PLAN의 TITLE, SCHEDULED_DATE, CHANNEL | 모두 NULL | 활동 제목과 예정 날짜는 필수 입력이고, 홍보 채널은 인스타그램, 매장 안내, 블로그, 기타 중 하나를 항상 고름 ([355줄](../../02_제품/화면시안/app.js#L355)) | 제목이나 날짜가 없는 계획이 저장될 수 있음 | 세 컬럼을 NOT NULL로 바꿈 |
| P10 | EXECUTION_RECORD.IS_EXECUTED | NULL | 실행 여부는 세 가지 중 하나를 항상 고름 ([361줄](../../02_제품/화면시안/app.js#L361)) | 실행 여부를 모르는 기록이 생길 수 있음 | NOT NULL로 바꿈 (P14와 함께 고침) |
| P11 | RECOMMENDATION_CRITERIA의 DECLINE_RATE_THRESHOLD, SOURCE_PERIOD_INFO, REASON_TEMPLATE, REQUIRED_CONDITION | 모두 NULL | 네 칸 모두 필수 입력 ([276줄](../../02_제품/화면시안/app.js#L276)) | 기준율이 비어 있으면 제안을 계산할 수 없음 | 네 컬럼을 NOT NULL로 바꿈 |
| P12 | DATA_SOURCE의 FILE_NAME, SOURCE_VERSION, START_DATE, END_DATE, UNIT | 모두 NULL | CSV 파일, 출처·버전, 기준기간 시작과 종료는 필수이고, 단위는 만 명과 억 원 중 하나를 항상 고름 ([238줄](../../02_제품/화면시안/app.js#L238)) | 어떤 자료인지 알 수 없는 등록 기록이 생길 수 있음 | 다섯 컬럼을 NOT NULL로 바꿈 |
| P13 | USERS의 EMAIL, PASSWORD, ROLE | 모두 NULL | 이메일과 비밀번호는 필수 입력이고, 역할은 사업체 운영자와 서비스 운영자 중 하나를 고름 ([289줄](../../02_제품/화면시안/app.js#L289), [291줄](../../02_제품/화면시안/app.js#L291), [292줄](../../02_제품/화면시안/app.js#L292)) | 로그인할 수 없는 계정이 생길 수 있음 | 세 컬럼을 NOT NULL로 바꿈 같은 이메일로 계정이 두 개 생기지 않도록 EMAIL에 UNIQUE도 더함 |

## 4. C. 값의 형식과 관계 규칙이 다른 곳

| 번호 | 대상 | 지금 상태 | 프로토타입 기준 | 쉽게 말하면 | 바꾸기로 하면 |
| --- | --- | --- | --- | --- | --- |
| P14 | EXECUTION_RECORD.IS_EXECUTED | CHAR(1) (예 또는 아니오 한 글자) | 실행함, 미실행, 확인 중 세 가지 ([361줄](../../02_제품/화면시안/app.js#L361), [73줄](../../02_제품/화면시안/app.js#L73)) | 예와 아니오 두 가지로는 '확인 중'을 저장할 수 없음 | 이름을 EXEC_STATUS로 바꾸고 VARCHAR(10)으로 정함 저장할 코드값(예: DONE, NOT_DONE, CHECKING)과 뜻을 코드 설계서에 적음 |
| P15 | EXECUTION_RECORD.IS_ADOPTED | CHAR(1) | 미확인, 채택, 미채택 세 가지 ([361줄](../../02_제품/화면시안/app.js#L361)) | 두 가지 칸에 세 가지 뜻을 넣으려면 약속이 필요함 | 방법 1: CHAR(1)을 유지하고 Y는 채택, N은 미채택, 비어 있으면 미확인으로 코드 설계서에 적음 방법 2: P14처럼 상태 코드로 바꿈 팀 결정: 둘 중 하나 |
| P16 | RecordPlan 관계 (일정 → 실행 기록) | Cardinality가 Zero, One or More | 계획 하나에 기록 하나만 저장함 기록을 계획 ID로 찾아 덮어씀 ([220줄](../../02_제품/화면시안/app.js#L220), [493줄](../../02_제품/화면시안/app.js#L493)) | 지금 ERD로는 한 계획에 기록이 여러 개 생길 수 있음 | 관계의 Cardinality를 Zero or One으로 바꾸고 EXECUTION_RECORD.PLAN_ID에 UNIQUE를 더함 |
| P17 | PROMO_PLAN의 (BUSINESS_ID, SUGGESTION_ID) | 중복을 막는 규칙 없음 | 같은 제안을 두 번 담으면 '이미 담은 제안입니다'라고 막음 ([353줄](../../02_제품/화면시안/app.js#L353)) | 같은 제안이 일정에 두 번 들어갈 수 있음 | 두 컬럼 묶음에 UNIQUE를 더함 주의: Oracle은 이 묶음에서 제안 ID가 비어 있는 직접 추가 계획도 같은 사업체에서 두 번째부터 중복으로 막음 Oracle이면 UNIQUE 대신 저장할 때 프로그램에서 확인한다고 테이블 명세서에 적음 팀 결정: 최종 DBMS에 따라 방법 선택 |
| P18 | RecordPlan 관계의 삭제 규칙 | 따로 정하지 않음 (파일에서 확인하지 못함) | 계획을 지우면 연결된 실행 기록도 함께 지움 ([396줄](../../02_제품/화면시안/app.js#L396)) | 계획만 지워지고 기록이 남거나, 기록 때문에 계획이 지워지지 않을 수 있음 | 관계 Properties의 RI Actions 탭에서 부모 삭제(Parent Delete)를 CASCADE로 정함 (PDF 42쪽) |

## 6. E. 새 엔터티가 필요한 부분 (팀이 정할 부분)

아래는 컬럼 몇 개를 더해서는 해결되지 않고 엔터티(표)를 새로 만들어야 하는 부분임 프로토타입은 예시 값으로 보여주거나 브라우저에만 저장하고 있어서, 지금 ERD로는 실제 서비스에서 저장할 곳이 없음

## 8. ERwin에서 고치는 방법

ERwin r7.3 기준이며, 메뉴가 보이지 않으면 다이어그램이나 엔터티를 오른쪽 클릭해 같은 이름의 메뉴를 찾음

- 길이, 자료형, NULL: Physical 화면에서 테이블을 오른쪽 클릭 → Column Properties → Physical Data Type과 Null Option을 고침 (PDF 46쪽)
- 컬럼 더하기: Logical 화면에서 엔터티 상자 안에 속성을 더한 뒤 Physical 화면에서 이름과 자료형을 정함 (PDF 39쪽, 46쪽)
- Cardinality와 삭제 규칙: 관계선을 오른쪽 클릭 → Properties → General 탭의 Cardinality, RI Actions 탭의 삭제 규칙을 고침 (PDF 42쪽)
- UNIQUE: 엔터티를 오른쪽 클릭 → Key Groups에서 새 키 그룹을 만들고 종류를 Alternate Key(AK)로 정한 뒤 컬럼을 넣음 이 기능은 PDF에 나오지 않음
- 새 엔터티와 관계: 도구 모음의 엔터티 도구와 1:N 식별·비식별 관계 도구를 씀 (PDF 37쪽, 40쪽)
- 바꾼 내용은 [ERD 수정 내역](ERD_수정_내역.md)에 날짜와 함께 적음
